# srtty — Plan 1 : cœur du pipeline (API → SRT/VTT/TXT)

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal :** une CLI `srtty <INPUT>` complète côté API. Elle extrait l'audio, le découpe sur les silences, transcrit en parallèle via un endpoint compatible OpenAI, construit les sous-titres à partir des mots et écrit SRT, VTT ou TXT, avec cache, `--speakers`, `--dry-run`, confirmation de coût, `--json` et des codes de retour fiables. La config s'écrit à la main dans ce plan ; `setup` arrive au plan 2.

**Architecture :** un seul crate lib + bin, en async (tokio, reqwest). C'est un pipeline linéaire, et la seule abstraction est le trait `Transcriber`. Les retries vivent dans l'orchestrateur (`run.rs`), pas dans le transcripteur, pour pouvoir les signaler. L'affichage passe par un trait `Reporter`. Ce plan livre `PlainReporter` (des lignes sur stderr) ; le plan 3 ajoutera le tableau de bord Ratatui derrière le même trait.

**Tech Stack :** Rust 1.99 (édition 2024), tokio 1.54, reqwest 0.13 (multipart, json, rustls), clap 4.6 (derive), serde/serde_json, toml 1.1, thiserror 2, miette 7 (fancy), async-trait, sha2 0.11, etcetera 0.11, futures 0.3. Tests : tempfile, wiremock 0.6, assert_cmd 2, predicates 3. ffmpeg et ffprobe sont des binaires système, appelés via `tokio::process::Command`.

**Spec :** `docs/superpowers/specs/2026-10-30-srtty-design.md` (et `docs/spikes/2026-10-30-openrouter-stt.md` pour les mesures).

**Découpage en plans** (chacun livre un logiciel utilisable) :
1. **Cœur** (ce plan).
2. `srtty models`, `srtty setup`, téléchargement et cache de `compat.json`, `srtty compat probe` et la CI hebdomadaire.

4. Backend local whisper-rs (feature `local`) et téléchargement des modèles dans `setup`.
5. Distribution : dist, binstall, Homebrew, CI des PR sous Linux et macOS, licences, README.

## Global Constraints

- Tous les textes destinés à l'utilisateur sont en anglais (messages, erreurs, aide). Libellé des intervenants par défaut : `Speaker`.
- Codes de retour : `0` succès, `1` usage, config ou E/S, `2` réseau, API ou modèle inadapté, `3` ffmpeg, `130` interruption.
- La clé d'API ne doit apparaître dans aucune sortie, aucun log, aucun `Debug` ni aucun message d'erreur.
- Aucun appel réseau pendant un run en dehors des requêtes de transcription. `compat.json` est lu depuis `<cache>/compat.json`, sinon depuis la copie embarquée.
- Audio envoyé : Opus 32 kbit/s, mono, 16 kHz, `-application voip`, conteneur Ogg.
- Requête : toujours `response_format=verbose_json` avec `timestamp_granularities[]=segment` et `timestamp_granularities[]=word`. Multipart par défaut ; `json-base64` sur demande de la config.
- Valeurs par défaut : `chunking.target_s = 300`, `chunking.jobs = 4`, `subtitles.max_chars_per_line = 42`, `subtitles.max_lines = 2`, `subtitles.max_duration_s = 7.0`, `subtitles.speaker_label = "Speaker"`, `confirm_above_usd = 1.0`.
- Découpage : fenêtre de ±30 s autour de la cible ; découpage seulement si `total - pos > target * 1.25` ; silences détectés avec `d=0.4` s et un seuil de `(mean_volume_db + 4.0).clamp(-50.0, -20.0)` dB.
- `--speakers` : une seule requête, refusée avant tout envoi si la durée dépasse 4500 s (75 min), si l'audio extrait dépasse 25 Mo ou si `compat.json` ne donne pas d'option de diarisation pour ce fournisseur et ce modèle.
- Segments « fins » : durée moyenne ≤ 10,0 s.
- Pas de fichier de sortie final en cas d'échec : écriture dans un fichier temporaire, puis renommage.
- Chemins XDG sur Linux et macOS : config `$XDG_CONFIG_HOME/srtty/config.toml` (défaut `~/.config/srtty/config.toml`), cache `$XDG_CACHE_HOME/srtty` (défaut `~/.cache/srtty`). `SRTTY_CONFIG` remplace le chemin de la config.
- CI locale de chaque tâche : `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings` et `cargo test` doivent passer avant le commit.

## Review Focus

1. **Premier morceau sans parole** (intro musicale, silence) : il ne doit pas faire conclure « modèle inadapté ». srtty passe au morceau suivant, séquentiellement, jusqu'à un morceau concluant. Si aucun ne l'est, il écrit des fichiers vides avec un avertissement. → test `first_chunk_without_speech_is_inconclusive` (tâche 11).
2. **Entrée courte ou sans parole** (< 1 s, ou aucun mot) : un SRT vide valide, un VTT réduit à `WEBVTT`, un avertissement `no speech detected` et le code 0, sans panic. → tests `render_empty_cues` (tâche 6) et `run_with_no_speech_writes_empty_files` (tâche 11).
3. **Audio sans silence près des cibles** (musique continue, débit ininterrompu) : coupe dure à la cible, morceaux contigus, aucune durée nulle. → test `plan_chunks_without_silences_cuts_at_target` (tâche 7).
4. **Chemins atypiques** : espaces ou unicode dans le nom, entrée sans extension, `-o` avec plusieurs formats. Chemins de sortie corrects et prévisibles. → test `output_paths_edge_cases` (tâche 6).
5. **Interruption (Ctrl-C) pendant la transcription** : aucun fichier final, les morceaux terminés restent en cache, code 130. → test `cancel_mid_run_leaves_no_output_and_keeps_cache` (tâche 11).

### Task 4 : normalisation des mots

**Files :**
- Create : `src/assemble/words.rs`, `src/assemble/mod.rs` (déclare seulement les modules à ce stade)
- Test : tests unitaires dans `src/assemble/words.rs`

Les fournisseurs renvoient trois formes de mots, mesurées au spike : des fragments à espace initiale (`" c"`, `"'est"` chez whisper-turbo), des mots nus coupés à l'apostrophe et sans ponctuation (`"C"`, `"est"` chez whisper-1), ou des mots entiers avec ou sans ponctuation. Le champ `text` porte presque toujours la ponctuation. La normalisation aligne d'abord `text` sur les timings des mots ; si l'alignement échoue, elle fusionne les fragments.

**Interfaces :**
- Consumes : `Transcript`, `Word`, `Segment`, `Usability` (tâche 3).
- Produces :
  - `normalize_words(t: &Transcript) -> Vec<Word>` : si `t.words` n'est pas vide, `align_text(&t.text, &t.words)` sinon, en cas d'échec, `merge_fragments(&t.words)`. Sinon, si `usability() == FineSegments`, `words_from_segments(&t.segments)`. Sinon, un vecteur vide.
  - `align_text(text: &str, tokens: &[Word]) -> Option<Vec<Word>>`
  - `merge_fragments(tokens: &[Word]) -> Vec<Word>` : si au moins un token commence par une espace, un token à espace initiale ouvre un mot et un token sans espace se colle au précédent ; sinon, les tokens sont gardés tels quels. Le texte est trimé.
  - `words_from_segments(segs: &[Segment]) -> Vec<Word>` : découpe le texte du segment sur les espaces et répartit `[start, end]` au prorata du nombre de caractères de chaque mot ; le speaker est conservé.

Algorithme de `align_text`, à suivre tel quel :

```
norm(s) = minuscules de s, en ne gardant que les caractères alphanumériques Unicode
i = 0 ; out = []
pour chaque d dans text.split_whitespace() :
    nd = norm(d)
    si nd est vide : si out n'est pas vide, out.last.text += " " + d ; sinon, mémoriser d en préfixe du mot suivant ; continuer
    acc = "" ; premier = None
    tant que len(acc) < len(nd) :
        si i == len(tokens) : retourner None
        nt = norm(tokens[i].text) ; i += 1
        si nt est vide : continuer
        premier = premier ou (i-1) ; acc += nt
        si nd ne commence pas par acc : retourner None
    out.push(Word { start: tokens[premier].start, end: tokens[i-1].end, text: d (avec l'éventuel préfixe), speaker: tokens[premier].speaker })
```

  - `Cue { start: f64, end: f64, lines: Vec<String>, speaker: Option<u32> }` (Clone, Debug, PartialEq). `speaker` est renuméroté à partir de 1 dans l'ordre de première apparition.

  - `build_cues(words: &[Word], rules: &CueRules) -> Vec<Cue>`
  - `filter_cues(cues: Vec<Cue>) -> Vec<Cue>` : retire les cues dont le texte normalisé est vide ; réduit toute suite d'au moins 3 cues consécutives au texte normalisé identique à la première de la suite.
  - `assemble(chunks: &[(f64, Transcript)], rules: &CueRules) -> Vec<Cue>` : normalise les mots de chaque morceau, ajoute l'offset du morceau aux timestamps, concatène, construit les cues, filtre, puis renumérote les intervenants.

Règles de `build_cues`, à suivre telles quelles. On parcourt les mots ; avant d'ajouter le mot `w` à la cue courante non vide, on ferme la cue si l'une de ces conditions est vraie :
- le speaker de `w` diffère de celui de la cue ;
- `w.start - précédent.end ≥ pause_break_s` ;
- la longueur du texte (mots joints par une espace) dépasserait `max_chars_per_line * max_lines` ;
- `w.end - cue.start > max_duration_s`.

Après l'ajout, on ferme la cue si le mot finit par `.`, `?`, `!` ou `…` (en ignorant un `»` final et les espaces), ou s'il finit par `,`, `;` ou `:` alors que le texte compte déjà au moins `max_chars_per_line` caractères.

À la fermeture : si la cue dure moins de `min_duration_s`, on prolonge sa fin jusqu'à `min(start + min_duration_s, début du mot suivant)`. Si le texte dépasse `max_chars_per_line`, on le coupe en deux lignes à l'espace qui minimise la longueur de la plus longue ligne. Un mot plus long que la ligne n'est jamais coupé.

**Files :**
- Create : `src/report.rs`, `src/run.rs`

**Interfaces :**
- Consumes : tâches 3 à 10.

  - `enum Stage { Extract, Split, Transcribe, Assemble, Write }`

  - `async prepare(input: &Path, reporter: &dyn Reporter) -> Result<Prepared, SrttyError>` : vérifie que l'entrée existe (sinon `Usage("input file not found: …")`), puis `ensure_ffmpeg`, l'empreinte sha256 de l'entrée, l'extraction dans un `TempDir`, la durée, le volume moyen et les silences (étapes `Extract` et `Split` signalées).
  - `RunRequest { formats: Vec<Format>, output: Option<PathBuf>, chunks_override: Option<Vec<(f64, f64)>>, target_s: f64, jobs: usize, opts: TranscribeOptions, rules: CueRules, speaker_label: String, cache: ChunkCache, cache_params: CacheParams, provider: String }`. `chunks_override = Some(vec![(0.0, total)])` sert à `--speakers` (tâche 12).
  - `async run(prep: Prepared, req: RunRequest, transcriber: Arc<dyn Transcriber>, reporter: Arc<dyn Reporter>, cancel: CancellationToken) -> Result<Summary, SrttyError>` : plan (`plan_chunks(prep.duration_s, req.target_s, &prep.silences, 30.0)` ou `chunks_override`), découpe, transcription, assemblage, puis écriture atomique de chaque format à côté de `prep.input` (ou selon `output`). Clé de cache : `ChunkCache::run_key(&prep.input_sha256, &req.cache_params)`.
  - `async transcribe_with_retry(t: &dyn Transcriber, chunk: &AudioChunk, opts: &TranscribeOptions, reporter: &dyn Reporter) -> Result<Transcript, TranscribeError>` : au plus 4 tentatives sur `Retryable`, avec une attente de `retry_after_s.unwrap_or(2^(n-1))` s plafonnée à 30 s (1, 2, 4 s), et un `ChunkRetry` émis avant chaque attente.
  - `CancellationToken` vient de `tokio_util::sync` : ajouter `tokio-util` aux dépendances.

Séquence de transcription, à suivre telle quelle :
1. Les morceaux sont transcrits **un par un, dans l'ordre**, tant qu'aucun n'est concluant : `Words` ou `FineSegments` est concluant ; `NoSpeech` passe au suivant ; `Unusable` donne `UnusableModel { model }`.
2. Dès qu'un morceau est concluant, les morceaux restants partent en parallèle, `jobs` au maximum (`futures::stream::iter(...).buffer_unordered(jobs)`).
3. Chaque morceau consulte le cache avant l'appel et y écrit après un succès.
4. Si `cancel` est déclenché, les requêtes en cours sont abandonnées, rien n'est écrit et le run renvoie `Interrupted`.
5. Si tous les morceaux sont `NoSpeech` : des fichiers vides (rendu de `[]`), l'avertissement `no speech detected` et `Ok`.
